# M8: Research scan

## Status: tooling done, acceptance run waiting on your target list

The acceptance criterion is "the scan runs on my targets.csv; findings.md and the charts are generated from the real run". Everything needed for that is built and tested. What's left needs you:

1. Compile `data/scan/targets.csv` by hand (200 to 500 rows; format in [data/scan/README.md](../../data/scan/README.md)). It is git-ignored, since it names real businesses.
2. On a machine with internet access and `make dev` running:

   ```bash
   make scan NAME=fall-2026        # vets the list, checks robots.txt, queues one page load per domain, waits
   make findings NAME=fall-2026    # writes docs/findings.md and docs/findings/*.png
   ```

3. Read `docs/findings.md` before committing it. It holds aggregates only, but you are the one publishing it.

No findings numbers appear anywhere in the repo yet, because no real scan has run. This container can't reach the public internet, and the list is yours to compile.

## What's built

| Piece | Where |
|---|---|
| Target loading: BOM-tolerant CSV, bare domains get `https://`, one row per registrable domain, rows that aren't a domain name skipped as `invalid_url` | `scan/targets.py` |
| robots.txt via `urllib.robotparser`, fetched through the SSRF egress proxy, RFC 9309 outcomes, `tag-monitor` token | `scan/robots.py` |
| `scan run`: all robots.txt checks first, then the scan, targets and jobs in one transaction; `--wait` polls progress | `scan/runner.py`, `scan/__main__.py` |
| `scan_url` job: per-domain lock, mobile capture, same checks as monitoring, capture JSON kept for re-analysis | `scan/job.py`, wired into `worker/__main__.py` |
| `scan analyze`: the §16 metrics with 95% Wilson intervals, LCP histogram with the 2.5 s and 4 s thresholds, share chart, by-category table (5-site minimum), methodology and limitations | `scan/analysis.py` |

Design: [ADR-016](../decisions.md#adr-016-the-research-scan-reuses-the-monitoring-pipeline-and-publishes-aggregates-only-m8).

## Evidence

**Tests.** `docker compose run --rm tests pytest -q`: **462 passed**. `tests/test_scan.py` covers:

- target vetting and domain names
- robots.txt outcomes (rules for everyone and for our token, 404, 500, an unreachable host, and a private address the proxy must block before any request reaches it)
- a whole scan run by a real worker against the fixture server
- the analysis on synthetic frames
- Wilson intervals, checked against known values and clamped for every n from 1 to 59
- the "no URLs or hostnames in the report" assertion

Ruff, ruff format and mypy are clean.

**A smoke run on the live compose stack.** The target list had only the demo page and three bad rows, no real sites: a duplicate domain, a typo with a space in the host, and a private IP. The commands:

```bash
docker compose run --rm --no-deps -v $SCRATCH:/smoke api \
  python -m tagmonitor.scan run --targets /smoke/targets.csv --name smoke-demo-2 --wait
docker compose run --rm --no-deps -v $SCRATCH:/smoke api \
  python -m tagmonitor.scan analyze --name smoke-demo-2 --docs-dir /smoke/docs
```

The output:

```
│ enqueued                 │ 1       │
│ skipped:duplicate_domain │ 1       │
│ skipped:invalid_url      │ 2       │
pending 1, done 0, failed 0
pending 0, done 1, failed 0
wrote /smoke/docs/findings.md (1 sites loaded)
```

One of the two worker containers picked up the job and loaded the page. The report and both charts were generated, with the Meta Pixel and GA4 counted as firing. That report is not committed, because it describes the demo page, not a real sample.

The first smoke run found a real bug. The typo and the private IP were counted as "attempted but unreachable", which would have deflated the reachability rate with data-entry mistakes. The fix is the domain-name check in `scan/targets.py`, with tests.
