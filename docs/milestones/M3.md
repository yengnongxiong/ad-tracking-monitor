## Design decisions to be ready to explain

1. **Network observation, not HTML search (ADR-008).** The product's value is catching "installed but not firing". Only the network shows it.
2. **One ordered question list for every tag (`tag_verdict.py`).** Not installed? Script blocked? Expected ids present? Page-view sent? More than once? Because Meta, GA4 and Ads walk the same list, a status means the same thing everywhere, and it's one function to test.
3. **Google = three checks (ADR-009)**, so each tag has its own alert state and a precise email.
4. **"Not evaluated" instead of five failures.** If the page doesn't load, only Page health fails; every other check returns `error`/`not_evaluated`, which the alert state machine (M5) ignores. One outage means one email.
5. **Plain-English copy in one module, with tests to keep it in sync.** Every check declares its possible codes, a test fails if any code lacks an explanation (or an explanation is stale), and `docs/check-explanations.md` is generated from the module, with a test that fails if it drifts.

## Deviations and refinements (please read)

- **`wrong_pixel` / `wrong_id` fires when *any* expected id is missing**, not only when none is seen (the PRD's wording). With two expected pixels and one removed, "none seen" would stay green, and that removal is exactly the regression we want to catch. For the common single-id case the two rules are identical.
- **Google split into three checks (ADR-009).**
- **Hits count when they leave the browser**, whatever the vendor responds.
- **`CheckResult.code`** is an addition: a machine-readable outcome alongside the status. It keys the explanations, and M4 stores it.
- **Fixture sites are http://**, so Page health correctly reports `not_https` for all of them. The other Page health outcomes are tested with https captures.
