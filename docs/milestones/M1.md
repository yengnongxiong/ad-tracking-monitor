## What's in the schema

`db/migrations/0001_init.sql` holds every table in PRD §11, the `site_latest_status` view, and nine indexes, each commented with the query it serves. Constraints worth knowing:

- `users.email` is `citext`, so emails are unique regardless of case.
- `jobs_active_dedupe_key_idx` is a **partial unique** index: at most one *queued or running* job per key. Finished jobs don't block new ones, and jobs without a key never conflict.
- `check_runs_owner_ck`: a run belongs to exactly one of a site or a scan (an XOR in SQL: `(site_id IS NULL) <> (scan_id IS NULL)`).
- `check_results` is unique on `(run_id, check_key)`.
- Deleting a user cascades to their sessions, sites, runs, results, states and alerts.

## Design decisions to be ready to explain

1. **Partial indexes for the queue.** `jobs_claim_idx` only contains `queued` rows. The table can hold millions of finished jobs, but the index the claim query walks stays tiny. Likewise, the partial *unique* index turns "one active capture per site" into a guarantee the database enforces, instead of a check in application code that can race.
2. **Every migration in its own transaction, plus an advisory lock.** A failing migration leaves no half-applied schema (tested: a broken `9999_broken.sql` leaves no trace). Two containers starting at once queue behind each other instead of racing (tested with two concurrent runners). *Alternative:* Alembic, which is heavier and generates code you have to review anyway; plain SQL is easier to read in an interview.
3. **Checksums on applied migrations.** Editing an applied file would leave dev and prod with different schemas and nobody would notice. The runner refuses to continue instead (tested). `.gitattributes` forces LF line endings so Windows checkouts don't trip it.
4. **The "worst device wins" view.** One job captures mobile and desktop. `site_latest_status` picks the newest job, then the worst status, so a pixel broken only on mobile still shows as broken. `error` ("couldn't evaluate") ranks lowest, so a check that failed to run never hides a real result.
5. **Tests use a separate `<db>_test` database**, recreated each session and truncated before every test that asks for `db`. Tests hit real Postgres (constraints, cascades and views are exactly what mocks get wrong) but never touch your dev data.

## Deviations from the PRD, and why

- `jobs.status` has no `'failed'` value. §12's outcome rules only ever produce `queued` (retry) or `dead`, so an unused state would just be a trap. Adding it later takes one line in a new migration.
- `sites.alert_email` is `NOT NULL`. The API (M6) fills it with the account email when the user leaves it blank, so alert delivery never has to handle a missing address.
